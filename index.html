Architecture · detection pipeline

  1. Drone input

    Video (RTSP/CSI camera) plus MAVLink telemetry, interpolated to a pose for every frame.

    hardware/ · telemetry.py
  2. Person detection

    Swappable detector: recorded detections for replay, or YOLO live.

    detection.py
  3. Geolocation

    Each detection is projected from pixels to ground coordinates.

    geolocation.py
  4. Ground-plane tracking

    ByteTrack-style two-stage association, done on the ground instead of in the image.

    tracking.py
  5. Analysis & deduplication

    Movement, persistence and location confidence; repeat sightings merge into one survivor.

    analysis.py
  6. Transparent priority

    A visible points table ranks each survivor HIGH / MEDIUM / LOW, with the reasons shown.

    priority.py
  7. Evidence & storage

    Annotated frame, crop and metadata per survivor, saved to SQLite.

    evidence.py · store.py
  8. Rescue command center

    A FastAPI API feeds the React dashboard: live feed, Leaflet map and survivor panel.

    main.py · frontend/

Results on the sample mission

12 / 12people found
0duplicate survivors
≈ 0.65 mmean location error

Key design decisions

  • Geolocate before tracking. The drone moves about 1 m per frame, so image-space matching falls apart for small people. Matching on the ground keeps tracks stable.
  • One pipeline for replay and live flight. A real UAV and edge computer replace only the inputs; nothing downstream changes.
  • Works without a backend. The web demo replays a precomputed mission, clearly labelled, so it always runs.

Pharma Reverse Chain Compliance Platform

Architecture · request path

  1. Role dashboards & public lookup

    Retailer POS, distributor, manufacturer, facility and regulator views, plus an unauthenticated batch-verify page.

    src/app/(app) · src/app/verify
  2. API route handlers

    Validate with Zod, authorise the role, then hand off. No business rules live here.

    src/app/api
  3. Domain core

    Eight invariants as pure functions, a fixed-order point-of-sale decision, and a single module allowed to change state.

    invariants.ts · pos.ts · lifecycle.ts
  4. Append-only ledger

    Every quantity movement appends a row; balances are always sums over the ledger.

    ledger.ts · transfer.ts
  5. Audit hash chain

    Each mutation appends a hashed audit event, so tampering is detectable by walking the chain.

    audit.ts
  6. PostgreSQL via Prisma

    Every mutation is one transaction; a failed invariant rolls the whole thing back.

    prisma/schema.prisma

How it catches fraud

Reuse a destroyed batch numberRegistry says DESTROYED → blocked at sale
Clone another real batch numberUnits billed exceed units issued → critical alert
Invent a batch numberNot in the registry → critical alert

Key design decisions

  • Rules live in one place. Routes never re-implement checks, so the code can't drift from the tests that cover it.
  • Both sides of every handoff. Each transfer writes the sender's and receiver's rows in one transaction, so stock can't appear from nowhere.
  • Tested end-to-end. Invariant, lifecycle and audit-chain unit tests, plus a script that drives the live server over HTTP.

Architecture · screening flow

  1. Gated sign-up

    Parents register with a clinician-issued invite code, the consent gate for children's health data under India's DPDP Act 2023.

    auth.routes.ts · clinician.routes.ts
  2. Child profile & session

    The Express API creates the child profile and opens a screening session.

    children.routes.ts · screening.routes.ts
  3. Games & questionnaire

    Four Phaser 3 game modules (gaze, imitate, sort, follow) stream behaviour events, alongside an M-CHAT-R/F questionnaire.

    game/scenes · EventCollector.ts
  4. Queued analysis job

    A Bull job (on Redis) hands the session to the FastAPI analysis engine.

    analysisService.ts
  5. Feature extraction & scoring

    MediaPipe face landmarks → engineered features → XGBoost score, compared against age-group baselines.

    landmark_extractor.py · scorer.py
  6. Live results

    Progress streams over Socket.io; results always show a screening-only disclaimer.

    Socket.io
  7. Clinician review

    A clinician reviews every result and can override the tier.

    clinician/ReviewPanel.tsx

Key design decisions

  • No “low risk” tier. Results are MONITOR, INDETERMINATE or ELEVATED; the system never clears a child outright.
  • One outlier is enough. A single metric more than 2 SD below the norm lifts the result to at least INDETERMINATE.
  • Honest about limits. A screening aid, not a diagnosis; baselines are marked approximate until validated on an Indian cohort.

Smart Attendance System

Hardware & ops

Architecture · from tap to dashboard

  1. RFID / face input

    A tap arrives with a face embedding; a simulator stands in for the real kiosk.

    rfid_simulator.py
  2. Anti-proxy check

    The face embedding is compared with the enrolled one (cosine similarity); mismatches are flagged.

    face_verification.py
  3. Impossible-travel detection

    Flags a tag used in two rooms faster than anyone could walk between them (haversine distance + max speed).

    anomaly_detector.py
  4. Local store

    Every tap writes to SQLite immediately, marked unsynced; the network never blocks a write.

    database.py
  5. Background sync

    Pushes queued rows to the central store when connectivity returns.

    sync_manager.py
  6. Risk analytics

    An explainable per-student risk score from attendance % and absence streaks.

    analytics.py
  7. Flask API & dashboard

    Live view with simulation controls for proxy, travel and offline scenarios.

    app.py · templates/ · static/

Key design decisions

  • Two independent signals. A face check stops handed-over cards; impossible-travel catches photo spoofing that fools the camera.
  • Offline-first. A Wi-Fi outage during a lecture never loses attendance; rows sync later.
  • Config-driven. Rooms, coordinates, classes and thresholds live in one JSON file, so another department can adopt it without code changes.
